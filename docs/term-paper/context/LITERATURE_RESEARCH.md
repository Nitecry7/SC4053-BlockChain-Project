# Research note: economic security of the SC4053 limit order book DEX

Prepared 23 November 2026. Source baseline: [GitHub `main`](https://github.com/Nitecry7/SC4053-BlockChain-Project/tree/main), with direct inspection of `README.md`, `SPEC.md` and `contracts/src/OrderBook.sol`. This is a research and paper-planning note, not a completed independent code audit or a report of newly executed tests.

## Executive conclusion

Recommend **Security**, narrowed to **economic security and market integrity in a gas-bounded on-chain limit order book**. Strong proposed title: *When Correct Settlement Is Not Fair Execution: Transaction Ordering, Dust Attacks, and Bounded Matching in an On-Chain DEX*.

The distinctive finding is not a generic unguarded reentrancy bug. The repository documents working `nonReentrant` and `SafeERC20` protections, and separate application-level attacks that exploit otherwise intentional matching rules. A regression test reportedly reproduces the profitable dust sandwich. Thus a rigorous thesis is: **accounting solvency and valid limit prices are necessary but insufficient for fair trade execution**. A local order-book prototype can preserve users' escrow and still cause a trader to receive a materially worse price than currently available in the resting book.

Security is arguably more consequential than privacy or scalability because every order can escrow assets and may settle at an economically adverse price. Scalability is causally connected to the attack: bounded work is necessary to control gas consumption, yet the 10-fill budget opens a strategic route around older, better orders. Privacy is real, since public transactions and addresses expose intentions and trading histories, but does not displace the market-integrity problem for this prototype. Avoid claiming it is a deployed exploit against public funds: README expressly says **local Anvil only**, chain 31337, no public mainnet deployment.

## Precisely verified architectural anchors

1. README describes a non-custodial limit-order-book DEX, **not an AMM**. One `OrderBook` per 18-decimal ERC20 token pair is deployed through `MarketFactory`. Price and time priority and maker-price settlement are advertised; the contract holds order escrow, not a pooled constant-product AMM reserve. A Next.js frontend and MetaMask submit user-signed transactions. No backend, indexer, or oracle is used. [README](https://github.com/Nitecry7/SC4053-BlockChain-Project/blob/main/README.md).
2. `OrderBook.sol` defines `MAX_MATCHES_PER_TX = 10`, `MAX_INSERT_SCAN = 100`, `LOT_SIZE = 1e9`, `TICK_SIZE = 1e9`, `PRICE_SCALE = 1e18`; both tokens must report 18 decimals. `_matchTaker` consumes the match budget on each fill. `_settleFill` transfers at **maker.price**, stores filled quantities, updates the last-trade price, and pays out of escrow. `placeLimitOrder` can insert an unfilled taker remainder after its budget expires. [`OrderBook.sol`](https://github.com/Nitecry7/SC4053-BlockChain-Project/blob/main/contracts/src/OrderBook.sol).
3. `matchOrders(maxMatches)` and `triggerStopOrders(maxCount)` are permissionless but require an external transaction and gas. Callers receive no reward. The latter checks the **single latest trade price** and uses a shared match budget across triggered stops. `cancelOrder` is restricted to the order's own trader. `ReentrancyGuard` covers the externally exposed state-changing methods. [`OrderBook.sol`](https://github.com/Nitecry7/SC4053-BlockChain-Project/blob/main/contracts/src/OrderBook.sol) and [`SPEC.md`, sections 5, 6, 8](https://github.com/Nitecry7/SC4053-BlockChain-Project/blob/main/SPEC.md).
4. The spec **documents the real application-level attacks** below, citing issue 007 and tests. This note verifies that the *claims exist in the source of truth*; it does not independently execute Foundry tests. Require a fresh test run and screenshots/log excerpts before claiming independent replication. [`SPEC.md`, section 8](https://github.com/Nitecry7/SC4053-BlockChain-Project/blob/main/SPEC.md).

## Threat model and four evidence-based considerations

| Consideration | Mechanism, evidence tier | Security effect | Existing defenses and remaining weakness |
|---|---|---|---|
| **1. Dust-assisted transaction-ordering sandwich** | SPEC §8 marks final-audit M-1, issue 007. Named regression `test_issue007_dustSandwichMakesAHonestBuyPayItsLimit`. Attacker gets ten one-lot asks executed first, exhausting the victim's 10-fill budget; the victim remainder rests as a bid at its limit price despite a cheaper ask still resting. Attacker then sells into that bid before matching clears the crossed book. **Documented reproduced behavior**. | Victim gets a worse execution price; attacker captures the difference, despite valid settlement and honest escrow accounting. The attack needs favorable ordering, so explain it as a conditional front-running scenario, not deterministic for every mined block. | Current price limit caps worst-case price but does not protect available best price. Gas and collateral for dust are economically small in demo units; transaction gas is nonzero. |
| **2. Stop-limit trigger manipulation and stop sniping** | `lastTradePrice` changes on any fill, regardless of size. Self-trading is allowed, and the user-facing trigger relies on that one price. SPEC §8 describes 10 dust bids exhausting the shared fill budget, leaving an activated sell stop crossed with a better bid, where attacker can fill at its wide limit price. **Documented scenario and independently reviewed reproduction according to SPEC**. | Premature or attacker-induced trigger activation, adverse execution at stop limit, additional gas/liveness exposure. The owner knowingly set a permissive stop limit; emphasize adverse execution relative to standing offers, **not execution below its stated limit**. | Stop limits bound execution but do not authenticate the reference price. No TWAP/VWAP, trade-size threshold or cooldown is implemented. |
| **3. Low-cost depth griefing and liveness** | `_tryInsert` scans at most 100 preceding orders. SPEC §8 says 101 tiny bids at a price can block less competitive bids with `BookTooDeep`; analogous for stop lists. Old Phase 6 design reportedly allowed a specially placed stop and dust to block all activations; that specific permanent blockage was fixed by refunding uninsertable activated stops. **Present depth limit; prior permanent-stop-block bug fixed**. | New traders may be denied order entry, triggers may be cancelled/refunded instead of resting, and prices can remain crossed until `matchOrders` is called. | Work caps prevent unbounded gas, but neither a numeric cap nor finer tick/lot granularity alone resolves incentive attacks. No keeper rewards for clearing crosses. |
| **4. Token-assumption and payout risk** | Contract uses `SafeERC20` but assumes exactly the requested transfer amount is received; only 18 decimals are checked, not fee-on-transfer or rebasing semantics. SPEC §8 explicitly says fee-on-transfer/rebasing unsupported and notes a malicious token's payout hook/blocklist can block settlement. **Declared unsupported token class and conditional risk**, not proven exploit against project-issued `DemoToken`. | Nonstandard tokens could break escrow accounting, cause reverts/denial, or leave direct donations stranded. | Token issuer's standard ERC20 `DemoToken` and `ReentrancyGuard` materially reduce risk for issued demo assets. For arbitrary listed ERC20 pairs, consider allowlisting standard tokens or balance-delta validation, while carefully preserving no-admin design. OWASP's 2026 SCWE-110 recommends tracking actual balance deltas. |

### Numerically illustrative dust sandwich (from SPEC)

`Bob`: a resting ask for 10 base tokens at 1.5 quote per base. `Carol`: buy 10 base, maximum limit 2.0. `Attacker`: inserts 10 sell orders of `LOT_SIZE = 10^9` base atomic units each at 1.499, immediately before Carol's transaction. Since a full base token is `10^18` units, each dust order has size `10^-9` base. Carol's ten fills consume only `10^-8` base at nearly 1.499 and exhaust the per-transaction count. Her balance remains mostly unfilled but now rests as a **bid maker** at 2.0. The attacker sells the remaining base at her maker price 2.0 and separately buys Bob's earlier 1.5 ask. For most of 10 units this can extract about 5 quote tokens before gas, fees and price effects. The exact arithmetic and assumptions are documented in SPEC §8; re-run the named regression test to cite expected and actual balance deltas. This is a **limit-order-book crossed-remainder sandwich**, not Uniswap AMM slippage along a constant-product curve.

### Explicitly avoid these errors in the term paper

1. Do **not** call the DEX an AMM, liquidity pool or oracle-based swap.
2. Do **not** write that reentrancy is currently exploitable without reproduction. The current contract explicitly uses `nonReentrant` and writes settlement state before external transfers.
3. Do **not** classify price-to-available-best as a conventional ERC20 theft or insolvent escrow. The mechanism moves value through an order whose limit price authorizes the settlement, while exploiting time priority and fill budget.
4. Do **not** write that final audit M-1 was patched. SPEC says mitigation was **not built** because changing matching rules late was considered too risky.
5. Do **not** equate prior fixed Phase 6 global blockage with current behavior. The current response to uninsertable activated stops is cancellation with refund, itself a partial liveness/service degradation.
6. Do **not** invent losses in real fiat or claim production deployment. Test tokens and Anvil mean empirical conclusions are within a deterministic test environment.
7. Do **not** rely on automated Slither output to establish economic fairness: static checks of classic reentrancy cannot substitute for adversarial ordering tests and invariants about best-price execution.

## Literature synthesis: contributions and applicability

| Paper or source | Source-backed contribution | Relevant application and limits |
|---|---|---|
| Daian et al., 2020, IEEE S&P [1] | Found frontrunning, priority gas auctions and miner-extractable value in early DEX transactions. | Establishes attacker ability and incentives to reorder public trade submissions. Does **not** specifically reproduce this custom 10-fill attack. |
| Zhou et al., 2023, IEEE S&P [2] | Systematized 181 real incidents and 77 papers across DeFi attacks. | Supports treating economic manipulation and interaction rules as security, not merely classic Solidity bugs. Do not infer one of its incidents is this project's exploit. |
| Heimbach and Wattenhofer, 2022, ACM AFT [3] | Compared transaction-ordering mitigations and their tradeoffs, finding no approach perfect across all criteria. | Justifies multi-layer recommendations and explicit fairness, latency, gas and openness tradeoffs. |
| Ferreira and Parkes, 2023, ACM STOC [4] | Proposed credible DEX design via verifiable sequencing rules. | Particularly close to **order-book execution ordering** and useful for formalizing fairness constraints. It is a substantial redesigned market mechanism, not a two-line local patch. |
| Canidio and Danos, 2024, Management Science [5] | Analyzed commit-reveal protection; adds two messages and waiting time while hindering some front-running. | A possible longer-term option for concealing limit orders until commitment, with delayed execution and UX cost. Does not itself fix the contract's post-cap crossed remainder if all orders are revealed simultaneously. |
| Chemaya et al., 2024 conference, 2025 proceedings [6] | Measured effect of safer default slippage tolerances on Uniswap and Sushiswap, reporting a 54.7% reduction in trader losses for a dynamic Uniswap default in their evaluation. | Motivates safer *limit-price defaults* and transparent user warnings. This **AMM result does not quantitatively predict** outcomes on the SC4053 order book. |
| Guidi and Michienzi, 2025 [7] | Empirical paper on linked MEV strategies and continued economic exploitation despite countermeasures. | Useful newer evidence that composition of individually known behaviors matters. Dataset and profit statistics should not be transferred to Anvil. |
| Solidity 0.8.24 official security considerations [8] | External contract calls can introduce reentrancy; all on-chain state and transaction inputs are observable. | Technical baseline and secure coding reference. Code may meet these patterns while still violating economic fairness. |
| OpenZeppelin Contracts 5.x official API [9] | `ReentrancyGuard` and `SafeERC20` facilities; `Pausable` requires configured authorization to be effective. | Evidence of current controls and possible future design tools. Adding an admin pause creates centralization and censorship tradeoffs inconsistent with a roleless design. |
| OWASP SCWE-110, 2026 [10] | Fee-on-transfer token misaccounting can arise when internal credit assumes the requested amount arrived. | Directly reinforces unsupported-token warning and balance-delta or allowlist mitigation. |

## Ranked, realistic mitigation proposals

| Priority | Mechanism | Security improvement | Engineering/research tradeoff and validation |
|---|---|---|---|
| P0 | **Eliminate a crossed taker remainder:** if a taker hits the 10-fill cap while still crossing the opposite head, refund the unmatched escrow and close/mark partial outcome, rather than allowing it to rest as a crossed maker. Alternative: pre-clear the existing crossing before allowing incoming taker, with bounded processing and explicit revert/refund semantics. | Removes the precise victim transition used by issue 007 and some stop snipes. | Changes SPEC/API and expected order lifecycle. Re-run full Foundry and frontend tests. Property: no execution by a later taker should bypass an older best resting price when competing orders cross. Prove or fuzz under bounded gas. |
| P0 | **Minimum economically meaningful fill size or adaptive order anti-dust rule** plus minimum order notional. | Makes cheap consumption of the 10-fill cap harder. | Disadvantages small traders, asset-denomination complexity, and attacker can still pay more capital. Price-aware threshold better than raw base token amount. |
| P1 | **Authenticated stop trigger signal:** minimum size for price-setting trades; rolling TWAP/VWAP or multi-trade median with observation window; ideally reference an external oracle only when an appropriate source exists. | Reduces one-dust-fill price manipulation and self-trade trigger abuse. | Lag, gas/storage overhead, thin-market bootstrapping, oracle trust/availability and cross-market basis risk. No guarantee against sustained wash trades. Add tests covering two-account self-trade and threshold boundaries. |
| P1 | **Safer limit defaults and explicit worst-case quote UI:** pre-submit review states the max/min price, best visible book, potential crossed-book divergence, possible stale execution, and token amount. | Helps users avoid excessive value leakage even when ordering is adversarial. | Client validation can be bypassed; contract guardrails required for hard guarantees. Attacker can reorder after a quote, so display cannot promise a guaranteed best price. |
| P2 | **Keeper incentive and liveness design:** small capped reward for economically useful public match/stop trigger calls, or a deterministic supported relayer with no exclusive rights. | Encourages clearing crossed books and pending stops. | Who funds the reward, spam farming, and concentration risks. Reward alone does not eliminate exploitable state transitions during ordering. |
| P2 | **Selective token policy:** continue restricting official tests to simple standard ERC20; for arbitrary pair listing, reject incompatible assets through governance, validation or transfers based on actual balance deltas where sound. | Prevents accounting assumptions being violated by fee-on-transfer/rebasing tokens. | Balancing permissionless listing against admission control; even balance-delta fixes cannot automatically support rebases or sender/recipient blocklists. |
| Long-term | Commit-reveal order submission, frequent batch clearing, verifiable sequencing or encrypted mempool. | Addresses information and ordering asymmetries beyond the local engine. | At least two transactions, reveal-withholding, batch fairness design, gas and complexity. A stronger future architecture, not necessary to demonstrate the immediate P0 patches. |

## Test plan and research contribution

1. **Baseline replay:** checkout exact `main` commit SHA; run full `forge test` and targeted `forge test --match-test test_issue007_dustSandwichMakesAHonestBuyPayItsLimit -vvv`, plus named stop sniping and 101-depth tests. Store invocation, exit code, test logs, git SHA, gas cost, expected and observed ending balances.
2. **Adversarial model:** two honest traders and one adversary, all standard `DemoToken`, controlled ordering on a fresh Anvil chain, honest buy orders with 1.5 best ask vs 2.0 maximum, attacker inserts 0 to 10 dust orders. No real mainnet traffic. Record fill count, executed quantity, effective per-unit price, advantage to attacker, gas, and whether crossed head persists.
3. **Comparative experiment:** original implementation vs hypothetical/branch implementation that refunds a crossing remainder. Preserve other parameters. Report correct settlement, best-price fairness, liveness, gas and user outcome. A conceptual proposal without implementation must be labeled as such.
4. **Stop experiment:** minimum-size self-trade crossing stop trigger; establish whether and when stop activates; compare single last price to proposed time/volume-aware trigger. Do not claim oracle manipulation if there is no oracle.
5. **Invariant:** vault solvency can hold **simultaneously** with economic unfairness. Define a fairness property conditional on admitted orders and current best maker. Report counterexample trace, not a fake formal proof.
6. **Validity:** distinguish Foundry unit/fuzz/invariant checks, scratch-chain execution, mock-wallet browser, and actual MetaMask observations. No extrapolation to production security without independent audits and deployment testing.

## Paper structure recommendation

1. Abstract (~150–200 words): thesis, exact architecture, observed counterexample, mitigations and limitations.
2. Introduction and research question (~400 words): why economic security outranks privacy and scalability in this particular application.
3. Architecture and threat model (~500 words): wallet, token factory, market factory, order book, lot/tick price, gas limits, attacker capabilities.
4. Critical literature review (~700–1000 words): 3 themes, MEV and ordering, economic design fairness, mitigation tradeoffs, show where conventional AMM literature differs from this order-book study.
5. Application-specific analysis (~900 words): concrete issue 007 worked trace and stop limit / liveness cases; figure: order book before and after 10 dust matches; table: claimed protection vs exact limitation.
6. Mitigation and evaluation framework (~800 words): baseline/medium/long-term proposals, tradeoffs, reproducible test methods, measurable fairness criteria.
7. Limitations and conclusion (~300 words): local-only scope, no new public exploit, test/peer review limitations, unresolved tradeoffs.
8. References [1]–[12] and optional appendix with code excerpts, snapshots, test log evidence. Use course's `paper-template.pdf` for exact length/style rules before final formatting.
