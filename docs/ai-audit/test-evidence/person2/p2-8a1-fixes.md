## 2. R6: `aria-label` on a generic `<span>` (fixed)

- **Root cause:** `Amount` (`web/components/data/amount.tsx`) and `AddressChip` (`address-chip.tsx`) put `aria-label` on a plain `<span>` and set the visible digits `aria-hidden`. `aria-label` is a prohibited attribute on a role-less span (axe `aria-prohibited-attr`), so assistive technology is allowed to ignore it, which could leave the amount unannounced.
- **Change:** the label is removed. The exact value (full precision plus the symbol) is now visually hidden text (`sr-only`) and the visible digits stay `aria-hidden`, so the value is exposed once. `title` (tooltip), the displayed digits, `splitAmount` and `formatExact` are unchanged. The address chip does the same with the full address. One more role-less `<div aria-label>` that axe reported as "needs review" after the fix (`wallet-panels.tsx:79`, "Share of total supply held by this wallet") was given `role="group"`.
- **Regression test:** `web/components/data/amount.test.ts` (6 tests). Run against the **old** `amount.tsx`: `3 failed | 3 passed` (no `aria-label`, exact value as hidden text, zero value); against the new file: `6 passed`.
- **axe-core 4.14.0 (temporary, pinned, loaded from jsDelivr into scratch pages, not a dependency), 18 page views** (7 routes at 1586 px and 375 px, disconnected; `/` and `/trade` also connected): **before** (P2-8A) `aria-prohibited-attr` on 12 views and `label-content-name-mismatch` on 6; **after: 0 violations on all 18 views.**
- **Not claimed:** no screen reader was run. The change replaces a prohibited pattern with ordinary text; whether NVDA or VoiceOver read it well is **unverified** (procedure in section 6).
- Same pattern left in place, not exercised by axe because those states were not rendered: role-less `<div aria-label>` in `tx-status.tsx:31` and the three review boxes (`order-ticket.tsx:352`, `token-form.tsx:158`, `market-form.tsx:183`). Reported as **R6b** (Low): add `role="group"` the same way.

## 3. R7: accessible names that do not contain the visible text (fixed)

- **Root cause:** the connected wallet button had `aria-label="Wallet <full address>, open account menu"` while it shows the short address; the "Copy Address" button had `aria-label="Copy wallet address"` while it shows "Copy Address" (WCAG 2.5.3 Label in Name).
- **Change:** the wallet button's name is now `<short address>, open account menu` (starts with the visible text; the full address moved to `title`); the Copy button has no `aria-label` when connected (its text is its name) and "Copy Address (connect a wallet first)" when not. Appearance, copy behaviour and layout classes are unchanged.
- **Existing tests adapted, not weakened:** the browser suites located the button by the old name `/Wallet 0x/`; they now use `/open account menu/`. `e2e/trade.e2e.mjs` reads visible text without the new hidden `.sr-only` text, so its assertions still check what is drawn.
- **Regression assertions** (new browser test in `e2e/dashboard.e2e.mjs`, mock wallet): the accessible name starts with the visible text (Playwright's accessibility snapshot shows `button "0x7099…79C8, open account menu"` and `button "Copy Address"`); both controls take keyboard focus; Enter opens the account dialog and Escape closes it; Enter on Copy Address copies the connected address and the label turns to "Copied"; the wallet button fits inside the viewport with no horizontal overflow at 375, 390, 430, 768 and 1586 px. Result: `e2e:dashboard` 14 passed (13 before plus this test).
- axe `label-content-name-mismatch`: 0 on the 6 views that had it.

## 4. R1 and R2: RPC cost per block

### 4.1 Method
Same pages, chain state and windows as P2-8A (script `measure2.mjs` in the session scratchpad, derived from P2-8A's `measure.mjs`): Chromium with the mock wallet on the scratch build, requests to the scratch node counted by Playwright. **Initial load** = navigation until the network is idle plus 1.5 s, wallet not connected. **One new block** = `evm_mine`, then a 9 s window, wallet connected as Alice, three repeats (the table gives the first; the repeats were within 1). **Idle** = 60 s with the wallet connected and nothing happening, on the overview only. **HTTP** = POST requests. **Ops** = JSON-RPC calls (an array in one POST counts every element), so the two are reported separately.

### 4.2 Why every block re-read everything (reproduced)
`useLiveBlock` invalidated every query except `blockNumber`; the 65 HTTP requests on the overview broke down into `eth_call` 50, `eth_getBlockByNumber` 6, `eth_getCode` 5, `eth_blockNumber` 2, `eth_getLogs` 1, `eth_getBalance` 1. The 50 `eth_call`s included token name, symbol, decimals, `isFactoryToken`, the market's token addresses and the OrderBook constants, none of which can change.

### 4.3 Classification and the change
| Class | Reads | Per-block refresh now |
|---|---|---|
| Immutable | token `name`, `symbol`, `decimals`, `isFactoryToken`; OrderBook `PRICE_SCALE`, `LOT_SIZE`, `TICK_SIZE`, `MAX_MATCHES_PER_TX`, `MAX_INSERT_SCAN`; a market's `baseToken`/`quoteToken` (market page, deployment check, registry pairs) | **skipped** (`staleTime: Infinity`, `meta.scope = "static"`) |
| Code presence | `eth_getCode` of the five contracts | refreshed (a reset or an outage must show up) |
| Registry | token and market counts and lists | refreshed (they change when a token or market is created; kept simple) |
| Dynamic | balances, allowances, `totalSupply`, books, best prices, last trade, my orders, trade logs | refreshed |
| After a transaction, and on a chain reset | everything, static reads included | unchanged: both call a full invalidation (`isTransactionRefresh`, `queryClient.invalidateQueries()`) |

`useTokenDetails` and `useMarketSnapshot` were each split into a static and a dynamic `useReadContracts` (their return shapes are unchanged except that they no longer spread every field of one query; typecheck passes). New `web/lib/query-scope.ts` holds `staticQuery`, `isPerBlockRefresh` and `isTransactionRefresh`.

### 4.4 Cache-level verification (owner refinement 2)
- **`meta` survives wagmi:** wagmi's `useReadContracts` spreads `query` into `useQuery`; confirmed on the real cache. On the production build I located the app's `QueryClient` through the React fiber tree in Chromium and listed `getQueryCache().getAll()`: 29 entries on the overview, 3 carrying `meta.scope = "static"` with `staleTime: Infinity`.
- **After one mined block:** the 3 static entries had the same `dataUpdatedAt`; every dynamic `readContracts` entry that had been fetched was refetched (the two entries that did not change were disabled queries that had never run, `status: pending`).
- **After a chain reset** (`evm_snapshot`, three blocks, `evm_revert`, which put the head below the watcher's anchor): the notice appeared and all 3 static entries were refetched.
- **Vitest at the query-cache level** (`web/lib/query-scope.test.ts`, 7 tests; real `QueryClient`, real wagmi config on a fake transport): the tag is kept on the cached query; a block refresh refetches the dynamic read and not the static one; the transaction refresh and a full invalidation refetch static reads; a different contract address is a different query; a failing dynamic refetch reports `isError` and `isRefetchError`. **Mutation check:** making `isPerBlockRefresh` ignore the tag turns 2 of the 7 red; restored, 7 pass.
- Account switch and network switch: static keys carry the contract addresses and the chain id and never the account, so they are unaffected; dynamic keys still carry the account. Covered by the unchanged browser suites (account switch, wrong network, market switch) which all pass (section 5).

### 4.5 RPC unavailable: a gap found, not caused by this change (reported, not fixed)
After the page had loaded, I stopped the scratch Anvil (by pid) and waited 14 s. **No query errored and nothing on the page changed**: the overview still showed "Read from chain, refreshed every block", the block number and every balance (screenshot kept in the scratchpad). Cause (read from the code): all refreshes are triggered by a new block or by a user action, a dead node produces neither, and `useChainWatch` deliberately swallows its errors ("no evidence, so no claim"). The existing "unreachable" banner depends on the deployment-code query, which is only refetched on those triggers.

This predates the change (the same triggers existed before; I did not run the HEAD build against a dead node, so this is **inferred from the code**, not measured). It matters because the requirement is not to show cached data as current when the RPC is demonstrably unavailable. **Proposed fix (needs approval):** a cheap liveness query (`eth_blockNumber` through `client.request`, refetched every 5 s, `retry: 1`) feeding `failed` of `classifyDeployment`, so the existing banner appears and the existing `live` gating hides stale panels; plus a test that stops a fake transport. About 12 extra calls per minute. Logged as **R9** (Medium).

| Trade, initial load | 39 / 39 | 39 / 39 | **5 / 39** |

Per-block operations by method on the overview: before `eth_call` 50, `eth_getBlockByNumber` 6, `eth_getCode` 5, `eth_blockNumber` 2, `eth_getLogs` 1, `eth_getBalance` 1; after `eth_call` 30 and the same other five. Trade: `eth_call` 28 to 13. Tokens: 27 to 12. Idle: `eth_getBlockByNumber` 40 and `eth_blockNumber` 15, unchanged.

Reading the table: the selective refresh removes work (about 31% fewer operations per block on the overview, 35% on Trade, 36% on Tokens). Batching removes none of the work, only HTTP overhead (operations are identical in the last two columns). Initial load of Trade and Tokens does not change under the selective refresh because those first loads must read everything once. Idle polling is not changed (section 4.7).

### 4.7 Batching: adopted after parity checks
`web/lib/wagmi.ts`: `http(RPC_URL, { batch: true })`. Checks:
- `web/lib/rpc-batching.test.ts` (2 tests, a local fake JSON-RPC node on an OS-assigned port): with and without batching, the same six operations are sent, the revert, the node error and the missing receipt / missing transaction each fail only their own caller with the same error type, and the successful calls still resolve; six HTTP requests become fewer.
- The four browser suites ran on the batched build, including `e2e:hardening` (speed-up, cancel, replace, chain reset): `13 / 14 / 14 / 9` passed. The real-chain suites use their own viem clients, not this transport, so they do not test batching (they were run once for the regression).
- Limits: only Anvil was tested. A hosted RPC provider may cap batch sizes; this app targets the local node. Reads are still separate `eth_call`s, so they are still not atomic.
- **Not changed:** `use-chain-watch.ts` (owner refinement 1). It still reads the head and the previously seen block every 3 s, so a different hash at the same height is still caught (`chain-reset.test.ts` and the reset browser test pass). Idle cost (R3) is therefore unchanged and is a recommendation: skip the second read only if a test proves same-height hash changes stay detected.

## 6. R8: contrast (measured on the rendering; not a conformance claim)
axe still cannot resolve contrast over translucent glass (116 to 141 nodes "needs review" on the overview), so a second method was used (`contrast.mjs`, scratchpad): for each visible text run, take its computed colour and opacity, re-render the same page with all text made transparent, sample the real pixels behind the run's bounding box, and compute the WCAG ratio of the text colour (composited at its alpha) against each sampled pixel. A run "falls below" if the 5th-percentile pixel ratio is under 4.5 (3 for text of 24 px or more, or 18.66 px bold or more). Disabled controls are excluded. Six views: `/`, `/trade` (connected, 1586 and 375 px), `/tokens`, `/markets` (disconnected, 1586 px).

| View | Text runs | Below AA at p5 | Below AA at median |
|---|---|---|---|
| `/` 1586 | 159 | 6 | 6 |
| `/trade` 1586 | 68 | 2 | 2 |
| `/tokens` 1586 | 58 | 2 | 2 |
| `/markets` 1586 | 51 | 2 | 2 |
| `/` 375 | 142 | 10 | 7 |
| `/trade` 375 | 55 | 4 | 3 |

- The six desktop failures are the one-letter token badges (white "S" 2.4 to 2.8 and "N" 3.8 to 4.5 on the blue and violet avatars, 11 and 14 px bold). On the four desktop views every run below the threshold is one of these badges, so desktop body text, labels and numbers measured at or above 4.5 at the 5th percentile. The mobile views have more failing runs than I recorded: only the six worst per view were kept (mobile `/` has 10 at p5 and 7 at the median, `/trade` has 4 and 3), so the mobile result is **incomplete** and the remaining mobile runs were not inspected.
- Mobile: the same badges, `SGDx` and `per` at 11 px (4.38 to 4.52, marginal) and "Open Trade view" (median 7.28, 5th percentile 1.15: part of its box overlaps a bright glow; needs a look).
- **Limits (so this is not a compliance statement):** one browser and one rendering; hover, focus, disabled and error states not sampled; text over the wave illustration or animated glow depends on the frame; bounding boxes include some padding; the badge letters may be treated as decorative, which is a judgment for the owner; and WCAG's "large text" rule was applied by computed size only. Result: **partly measured, not "compliant"**. Reported as **R8** (Low to Medium): badge initials and a few 11 px captions.
- **Manual procedure for the owner:** in Chrome DevTools, pick the token badge letter, the "Open Trade view" link and `SGDx`/`per` on mobile with the contrast picker (Elements, Styles, colour swatch), check the reported ratio with the page at rest; then run a screen reader (NVDA on Windows with Brave, or VoiceOver) through the dashboard and Trade ticket and note whether each balance and price is announced once, with its symbol, and whether the wallet button reads as its address.

## 7. React Best Practices (skill invoked with the Skill tool in this phase)
Rules actually applied: **client-side data fetching: deduplicate and avoid refetching what cannot change** (R1: static reads), **avoid unnecessary work on updates** (the per-block predicate), **narrow what a refresh touches** (tag-based predicate instead of a blanket one). Rules considered and **rejected for this phase**: dynamic imports and bundle work (R5; needs a bundle analyzer first, no measurement made), `React.memo` (no measured render problem), SWR (the app already has TanStack Query), a new indexer or cache layer for logs (R4; documented limit, out of scope).

## 8. Recommendations deliberately not implemented

- Event-driven registry refresh, incremental `Trade` log cursor (R4), route-level code splitting (R5), a liveness probe (R9): future phase or owner decision.
- Fixing the five remaining role-less `aria-label` containers (R6b) and the badge contrast (R8): reported, not done.
